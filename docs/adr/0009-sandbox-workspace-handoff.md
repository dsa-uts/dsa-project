# Sandbox Workspace Handoff

Topology-Agnostic Manifests (ADR 0008) retire hostPath injection, so the Judge needs another way to (a) place the Sandbox Workspace (Submission plus declared input Artifact files, writable) and the Preset files (read-only `/preset`) into a sandbox Pod, and (b) collect declared output Artifact files afterwards. Any option must satisfy: mount-enforced read-only `/preset` (ADR 0001 — copying Presets into a writable directory is not acceptable), the sandbox namespace's default egress deny (or a tightly scoped exception), and the Isolated Job Workspace / Explicit Artifact Handoff / Private-by-Default principles. Expected scale: workspaces are MB-scale (submissions plus presets; Preset files stay in the hundreds of KB), ~100 users. We choose pods/exec streaming via a platform loader container: at this scale it is the simplest option that leaves the egress deny fully intact and keeps Explicit Artifact Handoff enforcement in the Judge.

## Considered Options

- **pods/exec streaming via a platform loader container (chosen).** The sandbox Pod carries two emptyDir volumes (workspace, preset) and a second platform-owned "loader" container that contains `tar` and a keep-alive entrypoint so it stays exec-able (a native sidecar also fits). The Judge execs into the loader to stream a tar of workspace and Presets in before running any Step, then runs Steps in the sandbox container, which mounts the workspace read-write and `/preset` with `readOnly: true`; output Artifacts are collected by exec'ing `tar` in the loader, which keeps Explicit Artifact Handoff enforcement in the Judge exactly as today. No new cluster components; the egress deny stays fully intact (exec rides the API-server/kubelet channel that Steps and `stdin.path` streaming already depend on); sandbox images need no `tar` because only the loader image does, and the loader image comes from the same GHCR org the admission policy already allowlists. Cost: throughput is bounded by the API-server exec channel, so large workspaces or Artifacts transfer slowly — acceptable at the expected MB scale.
- **Object storage (Seaweedfs) — rejected.** The Judge puts a workspace tar into Seaweedfs; the loader or an init container pulls and unpacks it (e.g. via a presigned URL) and pushes Artifacts back. Best throughput for large files and reuses the object storage already in the tech selection, but Seaweedfs is not yet designed or deployed — this decision would pull its design forward. The deciding factor: NetworkPolicy is enforced per Pod, not per container, so "egress allowed only during the init/loader phase" cannot be expressed — any Seaweedfs exception stays open while Steps run, exposing the object-storage API surface to untrusted submission code. Artifact upload from inside the Pod also moves part of Explicit Artifact Handoff enforcement out of the Judge.
- **Shared filesystem (RWX PVC via NFS or Seaweedfs CSI) — rejected.** Closest to the hostPath mental model with local-mount performance (no per-Job streaming), and `readOnly` mounts cover `/preset`, but it adds a CSI driver or NFS server to operate, and a shared data plane widens the blast radius between concurrent Jobs: per-Job subpath isolation needs its own design to keep Isolated Job Workspace and Private-by-Default (one misconfigured mount exposes other Jobs' private data).
- **Baking Preset files into the Sandbox Image at Resource build time (variant, rejected).** GitHub Actions already builds an image per Resource Version, so `/preset` could ship inside the image, leaving only the Submission and Artifacts for runtime handoff. Rejected: `presets.files` is declared per Workflow while `sandbox-images` are top-level and shared across Jobs and Workflows, so baking would force presets to become an image-level property (a schema change); the files would have to be injected at build time either by the user's Dockerfile (making `presets.files` unverifiable at registration) or by a platform-added build step (extra pipeline complexity); and with the loader, Presets ride the same tar stream as the workspace, so at hundreds of KB the transfer saved is negligible.
- **Keep hostPath (rejected).** Violates Topology-Agnostic Manifests (ADR 0008).

## Consequences

- The sandbox namespace's default egress deny needs no exception; the exec channel the Judge already uses for Steps and `stdin.path` streaming is the only data path in and out of a sandbox Pod.
- Workspace placement, Preset placement, and Artifact collection all stay enforced by the Judge; nothing inside the Pod holds credentials or upload rights.
- The loader's exact form (native sidecar vs. keep-alive regular container) is deliberately not fixed here; it is decided during `judge/` template implementation.
- The Judge must treat tar streams coming back from the loader as untrusted (path traversal, symlink/hardlink/device entries), consistent with the Artifact rules in docs/spec/resource.md.
- If workspaces ever grow well beyond MB scale, revisit the object-storage option.

# Sandbox Workspace Handoff

Status: proposed — candidate comparison recorded; the mechanism selection is pending a maintainer decision.

Topology-Agnostic Manifests (ADR 0008) retire hostPath injection, so the Judge needs another way to (a) place the Sandbox Workspace (Submission plus declared input Artifact files, writable) and the Preset files (read-only `/preset`) into a sandbox Pod, and (b) collect declared output Artifact files afterwards. Any option must satisfy: mount-enforced read-only `/preset` (ADR 0001 — copying Presets into a writable directory is not acceptable), the sandbox namespace's default egress deny (or a tightly scoped exception), and the Isolated Job Workspace / Explicit Artifact Handoff / Private-by-Default principles. Expected scale: workspaces are MB-scale (submissions plus presets), ~100 users.

## Considered Options

- **pods/exec streaming via a platform loader container.** The sandbox Pod carries two emptyDir volumes (workspace, preset) and a second platform-owned "loader" container that contains `tar` and a keep-alive entrypoint so it stays exec-able (a native sidecar also fits). The Judge execs into the loader to stream a tar of workspace and Presets in before running any Step, then runs Steps in the sandbox container, which mounts the workspace read-write and `/preset` with `readOnly: true`; output Artifacts are collected by exec'ing `tar` in the loader, which keeps Explicit Artifact Handoff enforcement in the Judge exactly as today. No new cluster components; the egress deny stays fully intact (exec rides the API-server/kubelet channel that Steps and `stdin.path` streaming already depend on); sandbox images need no `tar` because only the loader image does, and the loader image comes from the same GHCR org the admission policy already allowlists. Cost: throughput is bounded by the API-server exec channel, so large workspaces or Artifacts transfer slowly.
- **Object storage (Seaweedfs).** The Judge puts a workspace tar into Seaweedfs; the loader or an init container pulls and unpacks it (e.g. via a presigned URL) and pushes Artifacts back. Best throughput for large files and reuses the object storage already in the tech selection, but Seaweedfs is not yet designed or deployed — this decision would pull its design forward — and the sandbox namespace's egress deny needs a scoped exception (loader/init only, to the Seaweedfs service), adding a carve-out to the hardening story. Artifact upload from inside the Pod also moves part of Explicit Artifact Handoff enforcement out of the Judge.
- **Shared filesystem (RWX PVC via NFS or Seaweedfs CSI).** Closest to the hostPath mental model with local-mount performance (no per-Job streaming), and `readOnly` mounts cover `/preset`, but it adds a CSI driver or NFS server to operate, and a shared data plane widens the blast radius between concurrent Jobs: per-Job subpath isolation needs its own design to keep Isolated Job Workspace and Private-by-Default (one misconfigured mount exposes other Jobs' private data).
- **Baking Preset files into the Sandbox Image at Resource build time** (variant, combinable with any option above). GitHub Actions already builds an image per Resource Version, so `/preset` could ship inside the image, leaving only the Submission and Artifacts for runtime handoff. Not a standalone option; recorded as a variant.
- **Keep hostPath (rejected).** Violates Topology-Agnostic Manifests (ADR 0008).
